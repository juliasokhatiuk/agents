# Порівняння: naive RAG vs. Sentence‑Window Retrieval vs. Parent‑Child (Auto‑Merge) Retrieval

Мета: коротко й практично пояснити відмінності між трьома популярними стратегіями для Retrieval‑Augmented Generation (RAG), їх переваги/недоліки, приклади застосування та практичні рекомендації по налаштуванню.

Джерела (приклади й реалізації):
- "From Naïve Retrieval to Sentence Window Retrieval in RAG systems" (dev.to) — приклади реалізації й пояснення концепції sentence‑window.
- Grayson Adkins — notebook з експериментом sentence‑window (показав покращення Answer Relevance та Groundedness).
- LlamaIndex — AutoMergingRetriever / Auto Merging Retriever docs (реалізація parent/auto‑merge retrieval, HierarchicalNodeParser).

---

1) Короткі визначення

- Naive RAG (basic / chunked RAG)
  - Стандартний pipeline: розбити документи на фіксовані чанки (наприклад, 512–2048 токенів), створити ембеддинги, виконати similarity search по векторному індексу і підставити top‑k чанків у prompt для генеруючої моделі.

- Sentence‑Window Retrieval (SWR)
  - Ретрівер працює на рівні речень: знаходить найбільш релевантне речення(я) й додає до нього сусідні речення у вікні (наприклад, ±1 речення). Дає «тонку», контекстну підстановку релевантного факту разом з близьким контекстом.

- Parent‑Child / Auto‑Merging Retrieval
  - Документна ієрархія (parent/child): індексуються «leaf» (дрібні) ноди для швидкого similarity search, але коли виявляється, що кілька retrieved leaf‑нод походять від одного parent‑секції, система повертає (або «змерджує») більший parent‑блок (або рекурсивно зростає контекст) замість/плюс до окремих дрібних частин. Мета — уникнути фрагментації контексту і дати більш узгоджений, цілісний фрагмент документа.

---

2) Як працюють (технічно, спрощено)

- Naive RAG
  - Chunking → embeddings → vector search (top_k) → concat(top_k) → LLM prompt
  - Chunking: фіксовані розміри або просте розбиття за параграфами/символами.

- Sentence‑Window
  - Розбір документів на речення + збереження порядку/метаданих → індексація кожного речення (із посиланням на позначення вікна: prev/next) → similarity search на реченнях → для знайденого речення повертається вікно (target ± N сусідів).

- Parent‑Child / Auto‑Merge
  - Побудова ієрархічних нод (coarse → fine), leaf nodes індексуються у векторі, інші — в docstore → при retrieval: знайдені leaf nodes аналізуються групами по батьківським ID; якщо поріг збігу (наприклад, >= T% retrieved children належать одному parent) досягається — повертається parent (або збудовується змерджений фрагмент), інакше — повертаються leaf.

---

3) Порівняння за ключовими критеріями

- Точність дуже дрібних фактів (precision for facts)
  - Naive RAG: помірна → важко гарантувати, бо факт може бути «загублений» в великому чанку.
  - Sentence‑Window: висока → фокус на конкретному реченні + локальний контекст зменшує ймовірність зміщення факту.
  - Parent‑Child: висока для цілісних відповідей (коли кілька дрібних частин потребують з'єднання); краще, якщо треба узгоджений фрагмент.

- Когерентність / зв'язність контексту
  - Naive RAG: може бути висока (якщо чанки вже самодостатні) або низька (якщо чанки перемішують теми).
  - Sentence‑Window: зазвичай добра всередині вікна, але може бути фрагментарною, якщо релевантні речення розкидані.
  - Parent‑Child: найкраща, коли потрібен згуртований сегмент (зменшує ризик «фрагментації» інформації).

- Ризик галюцинацій / несумісних фактів
  - Naive RAG: вищий, якщо в чанках є суперечлива або зайва інформація.
  - Sentence‑Window: нижчий (більше фокусування на релевантному реченні + близький контекст).
  - Parent‑Child: нижчий для повних секцій, але може додати зайві деталі (більший контекст) — ризик граматично-логічних «переобтяжень» відповіді.

- Витрати токенів / latency / вартість
  - Naive RAG: залежить від розміру чанків і top_k; зазвичай середні/високі, якщо використовуються великі чанки.
  - Sentence‑Window: економить токени (повертає тільки маленькі вікна), як правило дає нижчу вартість генерації та швидший inference.
  - Parent‑Child: може збільшити токени, коли повертається parent (великий блок) — але дає кращу якість у випадках, де це потрібно.

- Складність впровадження
  - Naive RAG: найпростіший, мінімум логіки.
  - Sentence‑Window: помірна — потрібно надійно парсити речення, зберігати вікна та метадані.
  - Parent‑Child: вища — потрібно будувати ієрархію (parser), зберігати docstore + vectorstore, логіку змердження.

- Шкалірування на великих корпусах
  - Naive RAG: добре шкалюється технічно (звичайний векторний індекс), але може давати слабшу якість на довгих, різнорідних корпусах.
  - Sentence‑Window: індекс більше (кожне речення/вікно → більше нод), але retrieval швидкий; ефективний там, де важлива точність.
  - Parent‑Child: вимагає комбінованої інфраструктури (leaf vector index + parent docstore/запит на зростання контексту), добре підходить для великих структурованих документів (документи з розділами).

---

4) Коли використовувати що

- Naive RAG
  - Прототипи, low‑cost proof‑of‑concepts.
  - Коли документи вже поділені на смислові блоки (наприклад, статті/FAQ з короткими пунктами).
  - Коли важлива простота pipeline та мінімальні інженерні витрати.

- Sentence‑Window
  - Домени, що потребують високої точності факту: право, медицина, технічні довідники.
  - Коли факти локалізуються в реченні/сусідніх реченнях.
  - Коли важливо зменшити кількість токенів та знизити ризик галюцинацій.

- Parent‑Child / Auto‑Merging
  - Коли релевантні фрагменти часто фрагментовані по дрібних n‑чанках, але краще подавати цілі розділи (наукові статті, техдокументація, довгі політики).
  - Коли потрібно, щоб LLM мав доступ до узгодженого більшоґо контексту (наприклад, щоб правильно синтезувати кілька фактів з різних місць того ж розділу).
  - Коли є ресурс розгорнути docstore + логіку ієрархії.

---

5) Практичні параметри та поради

- Sentence‑Window:
  - window_size: зазвичай 1 (тобто центральне речення + ±1) або 2; експериментуйте. Більше вікно → більше контексту, але вищі токени.
  - similarity_top_k: 3–5 речень часто вистачає.
  - Парсер речень повинен добре працювати з мовою корпусу (або використовувати NLP sentence splitter).

- Parent‑Child:
  - Ієрархія chunk size: приклад на LlamaIndex — coarse 2048, mid 512, leaf 128.
  - Merge threshold: приклади — коли >50–66% retrieved leaves належать одному parent → піднімати parent.
  - Потрібна швидка access до docstore (щоб витягнути parent по id після векторного пошуку leaf).

- Загальні поради:
  - Комбінуйте підходи: sentence‑window + auto‑merge — можна спочатку шукати на реченнях, потім, якщо знайдені речення з одного parent значаться часто, підключити більше parent‑контексту.
  - Валідуйте метрики: groundedness (фактично прив'язана до джерел), answer relevance, context relevance, токен‑витрати та latency.
  - Використовуйте метадані (document id, offset, parent id) щоб відстежувати provenance.

---

6) Емпіричні спостереження (з прикладів у публікаціях/ноутбуках)

- Grayson Adkins (notebook, Paul Graham essays) показав: sentence‑window retrieval покращила Answer Relevance на ≈22.7% та Groundedness на ≈38.2% порівняно з basic (naive) RAG, при цьому зменшила загальну кількість згенерованих токенів (тобто економія вартості при кращій якості).

- LlamaIndex AutoMergingRetriever дає кращу когерентність у випадках, коли декілька релевантних leaf‑нод належать одному parent, і часто зменшує «шум» при синтезі відповіді (але підвищує розмір контексту коли мердж виконується).

---

7) Резюме (швидко)

- Якщо треба швидко і просто — naive RAG.
- Якщо потрібна висока точність фактів і мінімальні токени — sentence‑window (особливо в юридичних/медичних/технічних доменах).
- Якщо дані структуровані і релевантні фрагменти часто потребують подачі згідного розділу — використовуй parent‑child / auto‑merge; також хороше доповнення до sentence‑window у гібридній системі.

---

8) Пропозиції для наступних кроків (що протестувати в практиці)

- Експеримент: naive vs sentence‑window vs parent‑child на вашому корпусі, виміряти: groundedness, answer relevance, prompt tokens, latency.
- Тюнінг: для sentence‑window — спробувати window_size 0..3; для auto‑merge — різні пороги T (0.5, 0.66, 0.8).
- Протокол: зберігайте provenance (source id + offset) в метаданих, щоб мати чітку зв'язку між відповіддю LLM і джерелами.
